# 18. How should code handle InterruptedException?

> **Section:** Thread Fundamentals · **Level:** Architect / Tech Lead · **Related code:** `src/com/java/multithreading/interview/questions/InterruptDemo.java`, `SpuriousWakeupDemo.java`

## TL;DR

Treat `InterruptedException` as a **cancellation request**, not an error. Either **propagate** it (add `throws InterruptedException` up the stack) or **restore the interrupt status** with `Thread.currentThread().interrupt()` before returning. Never swallow it silently — doing so breaks cooperative cancellation.

## Deep Dive

### The three acceptable responses

| Response | When | Snippet |
| --- | --- | --- |
| Propagate | Method can declare the exception | `void run() throws InterruptedException` |
| Re-interrupt | Must catch, but can't propagate | `Thread.currentThread().interrupt();` |
| Convert | Translate to a domain error | throw `new MyTaskCancelledException(e)` — keep the cause |

### The anti-patterns

- `catch (InterruptedException e) { }` — swallows cancellation.
- `catch (InterruptedException e) { e.printStackTrace(); }` — logs but loses the signal.
- Catching `Exception` broadly and ignoring it (as the commented-out code in `InterruptDemo` warns against).

## Code Walkthrough

Correct propagation:

```java
// src/com/java/multithreading/interview/questions/SpuriousWakeupDemo.java
try {
    while (!ready) condition.await();
    System.out.println("condition met, proceeding");
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // restore status, then unwind
} finally {
    lock.unlock();
}
```

In `InterruptDemo` the intended handler (shown commented) re-interrupts after logging:

```java
catch (InterruptedException e) {
    System.out.println("Worker interrupted during sleep");
    Thread.currentThread().interrupt();   // preserve the interrupt status
}
```

## Architect / Tech-Lead Insights

- Establish a codebase rule: **`InterruptedException` must never be silently caught.** This is a repeatable lint/review item.
- Restoring the flag is essential when you catch-but-can't-throw; otherwise upstream cancellation logic (e.g., `Future.cancel`) sees a "completed normally" task.
- When translating to a domain exception, always set the cause (`new X(e)`) so the cancellation signal is not lost.

## Common Pitfalls

| Pitfall | Why it hurts | Fix |
| --- | --- | --- |
| Empty catch block | Cancellation silently ignored | Re-interrupt / propagate |
| Only logging it | Signal lost | Re-interrupt |
| Not preserving the cause | Debugging dead-end | Pass `e` as cause |
| Busy-waiting instead of interruption | Burns CPU | Use blocking + interrupt |

## Interview Q&A

**Q:** What does `InterruptedException` really mean?
**A:** Another thread requested this thread stop waiting and cancel.

**Q:** What is the minimum correct catch block?
**A:** `catch (InterruptedException e) { Thread.currentThread().interrupt(); }`.
