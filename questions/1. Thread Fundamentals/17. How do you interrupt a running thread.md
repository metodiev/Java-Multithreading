# 17. How do you interrupt a running thread?

> **Section:** Thread Fundamentals · **Level:** Architect / Tech Lead · **Related code:** `src/com/java/multithreading/interview/questions/InterruptDemo.java`

## TL;DR

Call `thread.interrupt()`. This sets the target's **interrupt status** flag. If the target is blocked in `sleep`, `wait`, `join`, or most interruptible I/O, it wakes up and throws `InterruptedException` (and the flag is cleared). If it is running, nothing happens immediately — the thread must **poll** `Thread.interrupted()` (clears the flag) or `isInterrupted()` (does not).

## Deep Dive

### The two ways to observe an interrupt

| Situation | Effect of `interrupt()` |
| --- | --- |
| Thread in `sleep/wait/join` | Throws `InterruptedException`; flag cleared |
| Thread in interruptible I/O (NIO) | Throws `ClosedByInterruptException` |
| Thread computing | Flag set; must be polled |

### Clearing behaviour

| Call | Clears flag? |
| --- | --- |
| `Thread.interrupted()` (static) | Yes |
| `thread.isInterrupted()` (instance) | No |

## Code Walkthrough

```java
// src/com/java/multithreading/interview/questions/InterruptDemo.java
Thread worker = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        System.out.println("Worker running...");
    }
    System.out.println("Worker exiting gracefully");
});
worker.start();
Thread.sleep(1600);   // let it run
worker.interrupt();   // set the flag
worker.join();
```

1. The loop condition polls `isInterrupted()`.
2. `interrupt()` flips the flag.
3. The worker falls out of the loop and exits cleanly.

The commented `Thread.sleep(500)` in the source shows the *blocking* case: interrupting would raise `InterruptedException`, which the handler should catch and re-interrupt.

## Architect / Tech-Lead Insights

- `interrupt()` is Java's portable cancellation primitive — it is exactly what `Future.cancel(true)` and `shutdownNow()` use under the hood.
- Prefer interrupt-driven cancellation for pooled/blocking work; reserve polling flags for tight compute loops.
- Every long-running loop should include an interrupt check so cancellation latency is bounded.

## Common Pitfalls

| Pitfall | Why it hurts | Fix |
| --- | --- | --- |
| Ignoring the interrupt flag | Thread never stops | Poll or let it throw |
| Swallowing `InterruptedException` | Loses the signal | Re-interrupt / propagate |
| Assuming `interrupt()` stops compute loops | Flag alone does nothing | Check the flag in the loop |
| Calling `interrupt()` on an unrelated thread | Confusing cancellation | Target only known workers |

## Interview Q&A

**Q:** Does `interrupt()` immediately stop a thread?
**A:** No — it signals; the thread must cooperate.

**Q:** Difference between the two status methods?
**A:** `Thread.interrupted()` clears the flag; `isInterrupted()` does not.
