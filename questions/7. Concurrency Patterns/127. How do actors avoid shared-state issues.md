# 127. How does the Actor model prevent shared state issues?

> **Section:** 7. Concurrency Patterns · **Level:** Practitioner to architect

## TL;DR

Actors avoid shared-state races by letting only the owner mutate state and sending messages.

## How it works

State is mutated only by its owning actor; other components send messages rather than accessing fields. This confines synchronization to message delivery. Do not leak mutable references in messages, and remember that actors can still fail, process stale messages, deadlock through request cycles, or overload unbounded mailboxes.

## Example

```java
record SetLimit(int value) {} // immutable message value
```

## Mermaid diagram

```mermaid
flowchart LR
    A[Peer sends message] --> B[Owner processes serially]
    B --> C[Reply without shared mutation]
```

## Architect insight

Partition ownership so independent actors progress, and define mailbox overload behavior.

## Common pitfall

Do not leak mutable state references; actors still fail and overload.
